# ResNet18 in PyTorch from Vitis AI Library on KV260

- **Vitis AI version:** 3.5 with PyTorch 1.13.1
- **Target board:** AMD Kria™ KV260 Vision AI Starter Kit
- **Runtime DPU application:** `kv260-benchmark-b4096`
- **Expected KV260 DPU fingerprint:** `0x101000016010407`
- **Last update:** 28 April 2026

This README is a complete tutorial for running the Vitis AI ResNet18 vehicle-color-classification flow on the KV260. It covers both:

1. the **host-side Vitis AI flow**: Docker setup, dataset/model preparation, quantization, compilation and target packaging;
2. the **board-side execution flow**: network setup, Internet sharing, DPU firmware installation, target transfer and execution.

The repository is assumed to contain the scripts and target files needed by the tutorial. The KV260 `.xmodel` generated by this flow must match the DPU fingerprint exposed by the `kv260-benchmark-b4096` firmware application.

# 1. Introduction

## 1.1 Rationale

This tutorial deploys a ResNet18-based convolutional neural network for **vehicle color classification**. The application classifies the color of a car object in an input image using the 15-class VCoR vehicle-color dataset.

The model is a ResNet18 network fine-tuned for the VCoR dataset and then processed through the Vitis AI stack to run inference on the KV260 DPU.

The VCoR classes are:

```text
beige
black
blue
brown
gold
green
grey
orange
pink
purple
red
silver
tan
white
yellow
```

## 1.2 Vitis AI Flow

The complete Vitis AI flow is:

1. prepare the dataset and model files;
2. optionally train or fine-tune the model;
3. quantize the floating-point model into an INT8 model;
4. compile the quantized model into a DPU-compatible `.xmodel`;
5. package the target directory;
6. copy the target package to the KV260;
7. install/load the KV260 DPU firmware application;
8. run the C++ VART application on the board;
9. measure top-1/top-5 accuracy and DPU throughput.

The scripts in the repository automate most of this flow. Still, it is recommended to read the README once before running the scripts, because host-side compilation and board-side execution are separate steps.

# 6. Compile the Model for KV260

The quantized model must be compiled for the DPU loaded on the KV260 board.

This repository targets the `kv260-benchmark-b4096` firmware application, whose expected DPU fingerprint is:

```text
0x101000016010407
```

The compilation flow should use an architecture JSON that explicitly targets this fingerprint:

```json
{
  "fingerprint": "0x101000016010407"
}
```

A typical compile command is:

```bash
cd /workspace/tutorials/PyTorch-ResNet18/files

CNN_MODEL=train_resnet18_vcor.xmodel

vai_c_xir \
  --xmodel ./build/quantized/${CNN_MODEL} \
  --arch ./arch_kv260_board.json \
  --output_dir ./build/compiled_kv260 \
  --net_name kv260_train_resnet18_vcor
```

Verify the compiled model:

```bash
xdputil xmodel ./build/compiled_kv260/kv260_train_resnet18_vcor.xmodel -l
```

Expected properties:

```text
fingerprint: 0x101000016010407
DPU Arch:    DPUCZDX8G_ISA1_B4096_0101000016010407
output shape: [1, 15]
```

Copy the compiled model into the target folder if the script has not already done it:

```bash
cp ./build/compiled_kv260/kv260_train_resnet18_vcor.xmodel \
   ./build/target_kv260/vcor/kv260_train_resnet18_vcor.xmodel
```

Create the target tarball:

```bash
cd ./build
tar -cvf target_kv260.tar target_kv260
```

The output archive to transfer to the board is:

```text
build/target_kv260.tar
```

# 7. Prepare the KV260 Board

This section is run on the host PC and on the KV260 board.

## 7.1 Connect the Cables

Connect:

1. USB-UART cable from host PC to KV260;
2. Ethernet cable from host PC to KV260;
3. KV260 power supply.

The serial console is used for first access and recovery. Ethernet is used for SSH, SCP and Internet sharing.

## 7.2 Open the Serial Console

On the host PC:

```bash
sudo apt update
sudo apt install -y putty

dmesg | grep -E "ttyUSB|ttyACM"
```

Find the serial device, for example:

```text
/dev/ttyUSB0
/dev/ttyUSB1
/dev/ttyACM0
```

Open the serial console:

```bash
sudo putty -serial /dev/ttyUSB0 -sercfg 115200,8,n,1,N
```

Replace `/dev/ttyUSB0` with the actual device.

Log in as:

```text
ubuntu
```

Use the password configured for your board image. If needed, set or reset the password from the serial console:

```bash
sudo passwd ubuntu
```

## 7.3 Configure the Direct Ethernet Link

### On the Host PC

Find the host Ethernet interface:

```bash
ip -br link
ip -br addr
```

This tutorial assumes it is:

```text
eno1
```

Configure it:

```bash
HOST_BOARD_IF=eno1

sudo ip addr flush dev ${HOST_BOARD_IF}
sudo ip addr add 10.42.0.1/24 dev ${HOST_BOARD_IF}
sudo ip link set ${HOST_BOARD_IF} up

ip -br addr show ${HOST_BOARD_IF}
```

Expected:

```text
eno1 UP 10.42.0.1/24
```

Check the physical link:

```bash
cat /sys/class/net/${HOST_BOARD_IF}/carrier
```

Expected:

```text
1
```

If it prints `0`, check the Ethernet cable and board port.

### On the Board

From the serial console:

```bash
BOARD_IF=eth0

sudo ip addr flush dev ${BOARD_IF}
sudo ip addr add 10.42.0.217/24 dev ${BOARD_IF}
sudo ip link set ${BOARD_IF} up

ip -br addr show ${BOARD_IF}
```

Expected:

```text
eth0 UP 10.42.0.217/24
```

### IP Subnet Note

The IP addresses used for the direct host-board Ethernet link are independent from the network used by the host PC to access the Internet. However, the two networks must not use the same subnet.

For example, if the host PC is connected to Wi-Fi on:

```text
192.168.1.0/24
```

then this direct Ethernet configuration is safe:

```text
Host Ethernet:  10.42.0.1/24
Board Ethernet: 10.42.0.217/24
```

If the host PC is already using the `10.42.0.0/24` subnet for Internet access, choose another private subnet for the direct board link, for example:

```text
Host Ethernet:  192.168.50.1/24
Board Ethernet: 192.168.50.2/24
```

The rule is:

```text
Host and board must be on the same subnet.
The host-board subnet must not conflict with the host Internet subnet.
```

Check the host network configuration with:

```bash
ip route | grep default
ip -br addr
```

## 7.4 Ping and SSH Test

From the host PC:

```bash
ping -c 4 10.42.0.217
```

From the board:

```bash
ping -c 4 10.42.0.1
```

If both pings work, connect by SSH:

```bash
ssh ubuntu@10.42.0.217
```

## 7.5 Share Host Internet with the Board

The board needs Internet access to install Kria packages. The host PC routes the board traffic to the Internet using IPv4 forwarding and NAT.

### On the Host PC

Find the host Internet interface:

```bash
ip route | grep default
```

Example:

```text
default via 192.168.1.1 dev wlp2s0 proto dhcp metric 600
```

Set variables:

```bash
HOST_BOARD_IF=eno1
HOST_INTERNET_IF=$(ip route | awk '/default/ {print $5; exit}')

echo "Host-board interface: ${HOST_BOARD_IF}"
echo "Internet interface:   ${HOST_INTERNET_IF}"
```

Make sure `HOST_INTERNET_IF` is not the same as `HOST_BOARD_IF`.

Enable forwarding:

```bash
sudo sysctl -w net.ipv4.ip_forward=1
```

Optional persistent forwarding:

```bash
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-kv260-ip-forward.conf
sudo sysctl --system
```

Add NAT forwarding rules:

```bash
sudo iptables -t nat -C POSTROUTING -o ${HOST_INTERNET_IF} -j MASQUERADE 2>/dev/null || \
  sudo iptables -t nat -A POSTROUTING -o ${HOST_INTERNET_IF} -j MASQUERADE

sudo iptables -C FORWARD -i ${HOST_BOARD_IF} -o ${HOST_INTERNET_IF} -j ACCEPT 2>/dev/null || \
  sudo iptables -A FORWARD -i ${HOST_BOARD_IF} -o ${HOST_INTERNET_IF} -j ACCEPT

sudo iptables -C FORWARD -i ${HOST_INTERNET_IF} -o ${HOST_BOARD_IF} -m state --state RELATED,ESTABLISHED -j ACCEPT 2>/dev/null || \
  sudo iptables -A FORWARD -i ${HOST_INTERNET_IF} -o ${HOST_BOARD_IF} -m state --state RELATED,ESTABLISHED -j ACCEPT
```

### On the Board

Configure gateway and DNS:

```bash
sudo ip route replace default via 10.42.0.1 dev eth0

printf "nameserver 8.8.8.8\nnameserver 1.1.1.1\n" | sudo tee /etc/resolv.conf
```

Test Internet:

```bash
ping -c 4 10.42.0.1
ping -c 4 8.8.8.8
ping -c 4 google.com
```

Interpretation:

```text
ping 10.42.0.1 fails  -> host-board Ethernet is not correct
ping 8.8.8.8 fails    -> host NAT/routing is not correct
ping google.com fails -> DNS is not correct
```

Do not continue until the board can reach the Internet.

# 8. Install and Load the KV260 B4096 DPU Application

## 8.1 Update the Board Packages

On the board:

```bash
sudo apt update
```

Search for KV260 firmware packages:

```bash
apt search xlnx-firmware-kv260
```

You should see:

```text
xlnx-firmware-kv260-benchmark-b4096
```

## 8.2 Initialize Xilinx/Kria Package Sources if Needed

If the package is not visible:

```bash
sudo snap install xlnx-config --classic --channel=2.x
sudo xlnx-config.sysinit
sudo apt update
```

If apt asks what to do with a modified file such as:

```text
/etc/default/flash-kernel.oem-limerick-kria-meta
```

choose:

```text
keep the local version currently installed
```

If apt was interrupted or reports a broken package state:

```bash
sudo dpkg --configure -a
sudo apt -f install
sudo apt update
```

If a dialog asks which services should be restarted, keep the default selections and make sure `dfx-mgr.service` is selected. It is not necessary to restart display/session services such as `gdm`, `gdm3`, `dbus`, `systemd-logind`, or `user@*.service`.

If apt reports a pending kernel update, reboot after installation finishes:

```bash
sudo reboot
```

After reboot, reconfigure the board Ethernet if needed:

```bash
sudo ip addr flush dev eth0
sudo ip addr add 10.42.0.217/24 dev eth0
sudo ip link set eth0 up
sudo ip route replace default via 10.42.0.1 dev eth0
printf "nameserver 8.8.8.8\nnameserver 1.1.1.1\n" | sudo tee /etc/resolv.conf
```

## 8.3 Install the B4096 Firmware Package

On the board:

```bash
sudo apt install -y xlnx-firmware-kv260-benchmark-b4096
```

Restart the firmware manager:

```bash
sudo systemctl restart dfx-mgrd
```

List available accelerated applications:

```bash
sudo xmutil listapps
```

Expected: the list should include:

```text
kv260-benchmark-b4096
```

If the list still shows only:

```text
k26-starter-kits
```

then the DPU firmware package is not installed or not registered correctly.

## 8.4 Load the B4096 DPU Application

On the board:

```bash
sudo xmutil unloadapp
sudo xmutil loadapp kv260-benchmark-b4096
```

Check active applications:

```bash
sudo xmutil listapps
```

Check the DPU runtime:

```bash
xdputil query
show_dpu
```

Both commands must run without segmentation faults.

The board DPU fingerprint should match:

```text
0x101000016010407
```

The compiled `.xmodel` produced by this tutorial should target the same fingerprint.

# 10. Troubleshooting

## 10.1 `hostname -i` Prints `127.0.1.1`

Do not use `hostname -i` to identify the host Ethernet IP.

Use:

```bash
hostname -I
ip -br addr
```

The host Ethernet interface connected to the board should be:

```text
10.42.0.1/24
```

## 10.2 Board Cannot Be Pinged

On the host:

```bash
ip -br addr show eno1
cat /sys/class/net/eno1/carrier
ip route get 10.42.0.217
```

Expected:

```text
eno1 has 10.42.0.1/24
carrier is 1
route uses eno1
```

On the board:

```bash
ip -br addr show eth0
ip route
```

Expected:

```text
eth0 has 10.42.0.217/24
default route goes via 10.42.0.1
```

## 10.3 Board Has No Internet

On the board:

```bash
ping -c 4 10.42.0.1
ping -c 4 8.8.8.8
ping -c 4 google.com
```

On the host:

```bash
sudo sysctl net.ipv4.ip_forward
sudo iptables -t nat -S
sudo iptables -S FORWARD
```

## 10.4 `xmutil listapps` Shows Only `k26-starter-kits`

Install and register the B4096 firmware package:

```bash
sudo apt install -y xlnx-firmware-kv260-benchmark-b4096
sudo systemctl restart dfx-mgrd
sudo xmutil listapps
```

Then load it:

```bash
sudo xmutil unloadapp
sudo xmutil loadapp kv260-benchmark-b4096
```

## 10.5 `xdputil query` or `show_dpu` Segfaults

The DPU application is not correctly loaded.

Run:

```bash
sudo xmutil listapps
sudo xmutil unloadapp
sudo xmutil loadapp kv260-benchmark-b4096
xdputil query
show_dpu
```

If it still fails:

```bash
dmesg -T | grep -Ei "dpu|xrt|zocl|xclbin|dfx|firmware|segfault|xilinx" | tail -100
```

## 10.6 Fingerprint Mismatch

The compiled model and loaded DPU must have the same fingerprint.

Expected for this tutorial:

```text
0x101000016010407
```

Check the model:

```bash
xdputil xmodel /home/ubuntu/target_kv260/vcor/kv260_train_resnet18_vcor.xmodel -l | grep fingerprint
```

Check the board DPU:

```bash
xdputil query | grep -i fingerprint
```

If they differ, use the KV260 `.xmodel` generated by this repository for the `kv260-benchmark-b4096` DPU package.

Typical error:

```text
CHECK fingerprint fail !
model_fingerprint ...
dpu_fingerprint ...
fingerprint check failure
```

## 10.7 Runtime Produces No Predictions

If the accuracy script reports zero predictions, first check whether the CNN executable failed:

```bash
cd /home/ubuntu/target_kv260/vcor

./cnn_resnet18_vcor \
  ./kv260_train_resnet18_vcor.xmodel \
  ./test/ \
  ./vcor_labels.dat \
  2>&1 | tee ./rpt/predictions_debug.log

echo "pipeline statuses: ${PIPESTATUS[@]}"
```

If the first status is non-zero, fix that runtime error before checking accuracy.

Check the test images:

```bash
find ./test -maxdepth 1 -type f | wc -l
find ./test -maxdepth 1 -type f -iname "*.png" | wc -l
```

Expected:

```text
300
300
```
